    固定优先级

    优先级高的就绪任务先运行。优先级只是调度权重，不等于“任务更重要”的安全等级；配置可用优先级数量由 configMAX_PRIORITIES 决定。

    抢占与时间片是两件事

    configUSE_PREEMPTION 控制抢占行为；configUSE_TIME_SLICING 控制抢占模式下同优先级任务是否在 tick 检查中轮转。关闭时间片不等于关闭高优先级抢占。

    就绪不等于运行

    就绪：条件满足，等待 CPU。运行：当前正占用 CPU。阻塞：等事件或超时。挂起：显式停止参与调度。一个任务在单核上同一时刻不会既运行又阻塞。

    相对延时与周期任务

    vTaskDelay(n) 从调用点起至少阻塞指定 tick 数；任务本轮执行时间会叠加到周期上。周期循环常用 xTaskDelayUntil() / vTaskDelayUntil()，按上一次唤醒时刻推进目标时间，减少周期漂移。

{
    TickType_t lastWake = xTaskGetTickCount();
    const TickType_t period = pdMS_TO_TICKS( 20 );

    for( ;; )
    {
        read_sensor();
        xTaskDelayUntil( &lastWake, period );
    }
}

    示例中的 20 ms 是演示应用选择的周期，不是 FreeRTOS 默认值；可用精度受 tick 配置与目标硬件限制。

    03 / KERNEL OBJECTS

    内核组件地图：数据如何移动、任务如何等待

    选择组件时先问：我需要传一份数据、发一个信号、等多个条件，还是保护一个共享资源？它们看起来都像“同步”，但源码保存的信息和唤醒规则不同。

    队列 Queue：带容量的值传递通道

    xQueueGenericSend() 将固定长度 item 复制进环形存储区；接收端复制到自己的缓冲区。队列满/空时，可以立即返回错误，或把调用任务挂到等待发送/接收的事件链表并阻塞到数据变化或超时。

    适用：任务之间传递小型固定长度消息；中断向任务投递事件；生产者和消费者速率不同。传指针时队列复制的是指针值，指针所指内存的所有权仍要由应用约定。

    常用：xQueueCreate、xQueueSend、xQueueReceive、ISR 版本 xQueueSendFromISR。

    queue.c · Queue_t 与发送/接收queue.h · API/语义

    信号量 Semaphore：资源计数或二元通知

    源码把信号量复用队列对象机制：计数信号量表达可用资源数量；二元信号量通常表达“有事发生”。信号量不携带应用数据。它适合任务与 ISR 通知任务处理完成事件。

    适用：计数有限资源、简单同步、ISR 事件通知。若需要表达“谁拥有资源”并使用优先级继承，应选 mutex，而不是把二元信号量当 mutex。

    常用：xSemaphoreCreateBinary、xSemaphoreCreateCounting、xSemaphoreTake/Give，ISR 调用对应 FromISR 形式。

    queue.c · Semaphore 与 Queue 共用结构semphr.h · 信号量 API

    互斥锁 Mutex：带所有者和优先级继承

    mutex 是有所有者语义的锁。低优先级任务持锁时，如果高优先级任务等待该锁，内核可临时提高持有者优先级；释放时依据持有的 mutex 状态恢复/调整优先级。它缓解优先级反转，但不是所有死锁的自动解法。递归 mutex 允许 owner 多次 Take，但必须用对应的 Recursive API 配对释放。

    适用：任务间保护共享外设、共享结构或不可重入驱动。Mutex 只允许持有者释放，API 仅用于任务上下文；锁内应避免长时间等待其他资源。

    常用：xSemaphoreCreateMutex、xSemaphoreTake、xSemaphoreGive；递归形式为 xSemaphoreTakeRecursive/GiveRecursive。

    queue.c · xTaskPriorityInherit 调用点tasks.c · xTaskPriorityInherit/Disinheritsemphr.h · Recursive Mutex API

    任务通知 Task Notification：定向到某个任务

    每个 TCB 可按 configTASK_NOTIFICATION_ARRAY_ENTRIES 配置保存通知值和状态。发送者指定一个任务；通知可以作为轻量事件/计数/位集合，并可阻塞等待。通知是“一个目标任务的值与状态”，不是可排队的多条任意消息。

    适用：单一接收任务的 ISR 完成通知、任务间轻量同步、计数事件。若要广播给多个任务或传递任意多条消息，选择事件组或队列。

    源码动作：eNoAction、eSetBits、eIncrement、带覆盖/不覆盖的值写入；wait/take API 决定如何读取和清除。

    常用：xTaskNotifyGive、ulTaskNotifyTake、xTaskNotifyWait 及索引版本。

    tasks.c · TCB 通知字段和实现task.h · 通知 API 与 eNotifyAction

    事件组 Event Group：一组可组合的条件位

    任务可等待“任意一个位”或“全部指定位”成立，并选择满足后清除等待位。事件组维护当前位图和等待任务链表；设置位时逐个检查等待条件。ISR 设置位会把回调请求排入 timer command queue，由 Timer Service Task 执行位更新和等待者检查。

    适用：等待多个模块初始化完成、多个异步条件的组合、多个任务观察一组状态。它表达条件集合，不适合承载大量数据。

    常用：xEventGroupSetBits、xEventGroupWaitBits、xEventGroupClearBits、xEventGroupSetBitsFromISR。

    event_groups.c · wait / deferred ISR callbackevent_groups.h · API 说明timers.c · pended function call

    Stream / Message Buffer：单写者与单读者通道

    Stream Buffer 用环形字节缓冲传连续字节；空间不足时可部分写入，读取也按可用字节数返回。Message Buffer 在数据前保存消息长度，只有空间足够容纳长度头和整条消息时才写入；接收缓冲太小时不会消费该消息。两者要求单写者、单读者；底层长度为 xLength 的环形区最多报告 xLength - 1 字节可用。

    适用：串口字节流、音频/传感器数据流，或一对一传递变长消息。多写者/多读者要在应用层串行化，或改用队列。

    常用：xStreamBufferSend/Receive、xMessageBufferSend/Receive、触发阈值配置。

    stream_buffer.c · 写入、长度头、接收stream_buffer.h · API 约束与触发级别

    软件定时器：把到期工作交给 Timer Service Task

    软件 timer 的 start/stop/reset 命令进入 timer command queue；timer service task 处理命令并在到期时运行 callback。回调运行在服务任务上下文，应保持短小且非阻塞；耗时工作交由其他任务处理。

    适用：周期状态刷新、超时检查、延后执行轻量工作。若回调需要耗时处理，就在回调里通知工作任务。

    常用：xTimerCreate、xTimerStart、xTimerStop；服务任务优先级/栈/命令队列长度来自配置。

    timers.c · Timer_t / prvTimerTasktimers.h · 配置和 API

    链表 List：内核内部的状态索引

    任务状态链表项所在的 list 表示它当前属于哪个状态队列；事件链表项用于等待某个队列、信号量或事件条件。ready list 按优先级分组；延时任务按唤醒 tick 有序插入，因此 tick 只需从头检查到第一个未到期任务。

    适用：理解 Ready / Blocked 转换、等待顺序和同级轮转时读它。它是内核内部数据结构，应用通常不直接操作。

    list.c · 有序插入/游标前进list.h · List_t / ListItem_t

    Queue Set：同时等待多个队列或信号量

    把多个成员加入 Queue Set 后，接收任务等待 set；成员变为可读/可 Take 时，set 中收到的是“哪个成员就绪”的句柄。任务必须先调用 xQueueSelectFromSet 选出成员，再从该队列接收或对该信号量 Take。

    适用：确实需要一个任务等待多个异构对象，且无法用单一队列/通知重构时。它属于较少使用的高级能力。

    限制：set 容量要覆盖成员可能积累的事件；源码明确提醒等待含 mutex 的 set 不会让 mutex owner 继承等待者优先级。

                二、哪些中断能调用 FreeRTOS API？配置按什么顺序做？
                
        
                
          
                应用设置 IRQ 优先级；阈值决定它能否调用内核 API
                
          
                “受 OS 管控”不是把某个外设中断注册给 FreeRTOS。应用/芯片 HAL 设置每个 IRQ 的 NVIC 优先级；具体 port 决定内核临界区怎样屏蔽中断。以下只讲使用 BASEPRI 的 Cortex-M port：FreeRTOS 用阈值屏蔽一段优先级范围，落在允许范围内的 ISR 才能调用 ISR 专用的 ...FromISR() API。
                
          
                
            
                ① 在 FreeRTOSConfig.h 定内核阈值
                configMAX_SYSCALL_INTERRUPT_PRIORITY 告诉这个 port：内核临界区要屏蔽到哪个优先级。对 BASEPRI port，它是按芯片已实现优先级位（CMSIS 常用 __NVIC_PRIO_BITS 表示）编码后写入寄存器的值，不能是 0。它只设边界，不会替 UART、DMA 等具体 IRQ 分配优先级。
                
            
                ② 在板级代码给每个 IRQ 设优先级
                用 NVIC_SetPriority(IRQn, priority) 或 HAL 设置具体中断，并在使能前完成。CMSIS 参数是未移位的逻辑优先级；Cortex-M 数值越小，紧急度越高。检查后续驱动/HAL 有没有改写这个值。
                
            
                ③ 按逻辑优先级值比较
                CMSIS 中断优先级和 BASEPRI 编码值不是同一种表示。先把阈值还原为 CMSIS 使用的未移位逻辑值 P_api，再与 IRQ 的逻辑值 P_irq 比较。满足所选 port 的分组规则后，边界如下；其他架构不能直接套用。
                
          
                
          
                P_irq < P_api数值更小，紧急度更高；BASEPRI 不屏蔽它不能调用任何 FreeRTOS API
                API 阈值P_api
                P_irq ≥ P_api数值达到阈值或更大；处于内核屏蔽范围可以调用对应的 ...FromISR() API
                
          
                关键是别把 CMSIS 参数和 BASEPRI 编码值直接比较
                /* P_api 是项目选择的、未移位的 CMSIS 逻辑阈值 */
configMAX_SYSCALL_INTERRUPT_PRIORITY = P_api << ( 8U - __NVIC_PRIO_BITS );  /* 编码后写 BASEPRI */

/* 比较前，把编码阈值还原成逻辑值 */
P_api = configMAX_SYSCALL_INTERRUPT_PRIORITY >> ( 8U - __NVIC_PRIO_BITS );

/* CMSIS 接收未移位的逻辑优先级 */

P_irq >= P_api  → 该 ISR 可调用 ...FromISR()
P_irq <  P_api  → 该 ISR 不得调用任何 FreeRTOS API

                设备 ISR
                来源是 UART、SPI、GPIO、DMA 等设备事件。驱动读取硬件状态，并用 ISR 安全 API 通知任务。设备中断周期由硬件事件决定，不等于系统 tick。

                port 的 tick 中断路径调用 xTaskIncrementTick()。Kernel 增加 tick 计数、检查到期任务，把超时任务移到 Ready，并在配置允许且需要时请求切换。Tick hook 也是配置项控制的可选路径。

                七、最容易出错的边界检查
                
        
                
          
                为什么限制 ISR 调用内核 API？保护内核状态，同时保留高紧急度中断的低延迟
                
          
                
            
                为什么限制
                队列、任务状态和就绪/事件链表是内核共享状态。内核更新它们时必须获得独占访问。例如 xQueueGenericSendFromISR() 会修改队列数据；若有等待接收任务，还会移除事件项并把任务加入 Ready 路径。临界区就是让这些更新不被另一个“也会改内核状态”的上下文插入。
                
            
                限制的到底是什么
                任何 ISR 都只能调用适用于中断上下文的 ...FromISR() API；普通任务 API 可能阻塞，不可在 ISR 中调用。除此之外，只有提供中断嵌套/优先级屏蔽边界的 port 才有“哪些优先级可以调用 FromISR”的额外限制。以使用 BASEPRI 的 Cortex-M port 为例：高紧急度、不会被内核临界区屏蔽的 ISR 不得调用任何 FreeRTOS API；这与任务优先级无关。
                
            
                不限制会如何
                若未屏蔽的高紧急度 ISR 调用 FromISR API，它可能抢占一个尚未完成的内核更新，再次修改同一队列、TCB 或链表。嵌套顺序会破坏内核对“独占访问”的假设，导致计数/链表状态不一致、任务漏唤醒、调度异常，甚至后续卡死或故障。错误未必每次都立刻复现。
                
          
                
          
                为什么还保留这组高优先级中断？它们可以不受内核临界区延迟，满足严格时限、低抖动的硬件响应需求；代价是它们必须完全不调用内核 API。不同 port 的屏蔽方式不同：有些只屏蔽一个优先级范围，有些会关闭所有普通可屏蔽中断，因此不能把 Cortex-M 的阈值规则推广到所有架构。
                
          
                允许调用 API 的 ISR 为什么能参与这套保护：在使用 BASEPRI 的单核 Cortex-M port 中，处于 syscall-safe 范围的中断（逻辑紧急度不高于阈值；按 NVIC 编码通常是优先级数值不小于 configMAX_SYSCALL_INTERRUPT_PRIORITY）会被内核临界区屏蔽，因此不会插入一段正在更新内核状态的任务代码。它们进入中断后只能用对应的 ...FromISR() API；这些路径会进入 ISR 临界区，更新内核状态时继续屏蔽同一可调用范围内的中断。这样单核上的任务与这些 ISR 按内核约定串行访问共享状态。高紧急度、未被该阈值屏蔽的中断不在这套互斥范围内，所以仍不能调用 API；任务版 API 也不会因为来自“安全优先级”的 ISR 就变成可用。
                
          
                “违规调用不一定马上出错”不等于“调用是安全的”：某一次调用若碰巧没有与被打断的内核路径访问同一状态，运行中可能看不到故障。但 FreeRTOS 没有承诺高紧急度 ISR 可以调用某个 FromISR API；API 的完整路径还可能因配置和运行状态走到不同内核操作。要证明安全，必须证明整个调用及其所有分支都不碰正在更新的内核状态，并维持队列、TCB、链表和调度状态之间的整体不变量。这里的“原子性”是这些多步状态转换的一致性，不只是单条机器指令或单个字段读写不可分割。因此使用 BASEPRI 阈值屏蔽的 port 按中断优先级类别禁止这类 ISR 调用任何内核 API；一次测试没复现，或只检查到一个字段，不能作为放宽规则的依据。

                ③ 高紧急度 ISR 插入BASEPRI 不屏蔽逻辑紧急度高于阈值的中断。若它在两次指针写入之间抢占任务，此单节点例子中 xListEnd.pxNext 仍指向该节点，pxContainer 仍指向原链表，计数仍为 1。listLIST_IS_EMPTY() 只检查 uxNumberOfItems，所以仍判为非空；接着 listGET_OWNER_OF_HEAD_ENTRY() 沿尚未改写的 xListEnd.pxNext 再次选中同一 TCB。若 ISR 对同一队列调用 xQueueGenericSendFromISR() 且优先级断言未启用，它就可能再次摘除该等待项。ISR 进入自己的临界区时设置 BASEPRI，只能限制后续可屏蔽中断；它既不能屏蔽当前高紧急度 ISR，也不能让已被打断的任务先完成半次链表操作。
                
            
                ④ 任务恢复执行内层 ISR 的摘除把该单节点链表计数从 1 减到 0。任务恢复后，外层 uxListRemove() 仍使用进入函数时保存的链表指针和节点指针，继续写入、清空 pxContainer，并再次递减计数。外层第二次递减使 UBaseType_t 计数从 0 无符号回绕到其最大值；链表链接已表示“空”，计数却表示“非空”。后续 listLIST_IS_EMPTY() 会作出错误判断，队首宏可能把 sentinel 当成任务节点继续处理；具体表现取决于配置与断言，可能是错误唤醒、无效 TCB 访问、卡死或故障。

                这不是泛泛的“防止数据被破坏”，而是源码明确依赖的互斥前提：
                • queue.c 的注释明确说明：逻辑紧急度高于最大系统调用优先级（Cortex-M 中通常表现为优先级数值更小）的中断，在内核临界区期间仍保持开启，因此不能调用任何 FreeRTOS API。
                • list.h 说明默认不把链表字段声明为 volatile：这些字段预期只在临界区或调度器挂起期间以“功能上原子”的方式修改；源码允许应用定义 configLIST_VOLATILE 改为 volatile，但这不会替代互斥。
                • tasks.c 对 xTaskRemoveFromEventList() 明确要求必须从临界区调用，并以此保证事件链表独占访问。上表的嵌套删除是违反这些前提后，从实际指针写入顺序推演出的一个具体反例。

                断言触发或行为异常时，按这条链核对
                1. 确认工程实际编译进来的 port，再读它要求的优先级阈值和分组规则。
                2. 查该 IRQ 最终生效的 NVIC_SetPriority()/HAL 配置；检查初始化后是否又被驱动改写。
                3. 把 IRQ 与阈值都换成 CMSIS 未移位逻辑值，再按 port 规则比较；不要直接比较编码后的 configMAX_SYSCALL_INTERRUPT_PRIORITY。

                ISR 必须短、非阻塞、明确失败策略
                • 不能在 ISR 中调用可能等待的任务版 API；使用对应的 FromISR 接口，并按 API 契约检查输出参数。
                • FromISR API 不会替应用扩容队列。队列满、流缓冲区空间不足、timer command queue 满，都需要明确丢弃、计数、重试或 DMA/FIFO 兜底策略。
                • 唤醒任务后先更新唤醒标记；在 ISR 退出前调用目标 port 要求的 yield 宏。
                • 不要在 ISR 中拿 Mutex，也不要把耗时解析、格式化日志、等待外设完成等工作塞进中断路径。
                • 高紧急度 ISR 若不能调用内核 API，可把必要数据放入设计好的缓冲区，再触发允许调用 API 的较低紧急度 ISR 或交由任务处理。

                页面里的数字，逐项回到源码核验
                基准是本工作区的 Kernel C/H 实现；目标项目若使用不同版本或 port，以实际参与编译的文件为准。先分清这是一项动画参数、源码条件，还是目标编译结果，再按下表核验。
                
        
                页面中的例子它是什么数字核验入口怎样核验 / 能得出什么
                
          
                调度动画 P3、P2、P0为讲清高低优先级而设的相对标签，不是这份源码配置出来的实际优先级数值。taskSELECT_HIGHEST_PRIORITY_TASK；configMAX_PRIORITIES看选择器如何从最高 Ready 优先级向下找非空列表；实际可用优先级数量取工程的 configMAX_PRIORITIES。
                
          
                队列动画 5 items、4 B/item界面可调的教学输入，默认值不是内核常量。数据区示意字节数按 uxLength × uxItemSize 算。xQueueGenericCreate、Queue_t.uxLength、Queue_t.uxItemSize、prvCopyDataToQueue改动画控件，观察容量和字节数；再看创建参数如何写入字段，以及发送时如何按 uxItemSize 复制。控制块大小不包含在这个乘积里。
                
          
                队列阶段目录（例如 97 帧）页面把源码路径拆成的讲解帧数，不是 FreeRTOS 内核定义的“阶段数”。不同案例和队列参数会生成不同帧。本页 buildQueueStory()；xQueueGenericSend、xQueueReceive阶段目录可跳到某一帧；阅读该帧的源码动作，再回到队列 API 的条件、复制、等待列表和重试分支。动画帧是教学拆分，不能当作源码语句数。
                
          
                软件定时器 3 演示 tick可调的案例周期，单位是内核 tick；不是固定毫秒数，也不代表真实板子的时钟周期。xTimerCreate、xTimerGenericCommandFromTask、prvProcessExpiredTimer；xTaskIncrementTick沿命令入队、daemon 处理、到期列表和 callback 路径读；要换算成时间，使用实际工程的 configTICK_RATE_HZ。
                
          
                sizeof(StaticTask_t)、sizeof(tskTCB)前者可从目标头文件与 ABI 编译得出；后者是目标编译器对私有结构体的实际布局结果。StaticTask_t；tskTCB在实际工程加入临时测量代码并读调试器结果。StaticTask_t 不公开 TCB 字段；要量 tskTCB，代码必须放在 tasks.c 类型定义可见处。
                
          
                堆剩余量、最大可分配块依赖选用的 heap 实现、碎片状态、对齐和头部开销；不能由一个“剩余字节数”推断。pvPortMalloc、prvInsertBlockIntoFreeList看当前 heap 实现如何切块、对齐和合并；在目标上检查空闲总量与最大连续块时，要把它们当成不同指标。
                
        
                
        
                
          
                实际工程里的公开类型
                “测量代码”是临时加入工程、把编译结果存进变量的几行代码，不是硬件探针。把它放进使用同一份 FreeRTOSConfig.h、编译器选项和目标 port 的应用文件，编译后在调试器查看变量：
                #include "FreeRTOS.h"
#include "task.h"
volatile size_t stackElementBytes = sizeof( StackType_t );
volatile size_t tickBytes = sizeof( TickType_t );
#if ( configSUPPORT_STATIC_ALLOCATION == 1 )
volatile size_t staticTaskBytes = sizeof( StaticTask_t );
#endif
                StackType_t stack[N] 的数组字节数为 N × sizeof(StackType_t)。测量结果只适用于这次目标构建。
                
          
                内核私有类型：从对象指针测量
                私有类型只在内核实现文件中可见。以 tasks.c 的 prvCreateStaticTask() 为例，源码把调用方提供的存储地址转换成 TCB 指针；保留已有两行，在函数体内临时加第三行：
                TCB_t * pxNewTCB;                         /* 源码已有 */
pxNewTCB = ( TCB_t * ) pxTaskBuffer;      /* 源码已有：指向实际 TCB */
volatile size_t taskControlBlockBytes = sizeof( *pxNewTCB ); /* 临时测量 */
                sizeof( *pxNewTCB ) 取得指针所指对象的 TCB 大小；写成 sizeof( pxNewTCB ) 则只会得到指针本身大小。sizeof 根据编译期类型布局计算，不会读取对象字段；指针在此用于说明所量的是哪个类型的对象。TCB 大小不含任务栈。
                队列可在 queue.c 的 xQueueGenericSend() 中对已有的 Queue_t * const pxQueue = xQueue 使用 sizeof( *pxQueue )；定时器和事件组也分别在各自实现文件中，对真实对象指针使用 sizeof( *pxTimer )、sizeof( *pxEventBits )。按目标配置构建并读取变量，然后移除临时代码；不同 #if 配置可能产生不同布局。队列控制块大小不含 item 数据区或分配器开销。
                
        
                
        
                读源码时的核验顺序
                先确认案例参数 → 找到对应 API 的入口条件 → 跟踪它修改的字段 / 链表 → 核对配置分支 → 只有涉及字节数或真实时间时，才用目标编译结果作结论。
